# Mục lục và điều phối hợp đồng API UniHub

> Đây là chỉ mục điều phối, không tuyên bố toàn bộ hợp đồng đã hoàn tất hoặc được duyệt. Leader là người duyệt cuối cùng cho mọi hợp đồng; các ý kiến TV2–TV5 là đầu vào, không thay thế phê duyệt. Chỉ contract Major và API đọc cơ hội đã được duyệt/triển khai. Các contract còn lại chờ leader review; một số quyết định riêng đã được chốt nhưng không làm cả contract thành approved.

## 5. Shared-file rules and PR slices

- TV1 coordinates `docs/api-conventions.md`, this index and shared auth/error contract; **leader approves all API contracts**. Module owners may submit technical evidence or suggestions, but cannot approve or close a contract themselves. Members implement only after leader approval.
- Routes are mounted by TV1 after leader-approved implementation PRs are reviewed. Changes to `backend/src/app.ts`, frontend router, shared API client, root scripts, schema/migrations/GRANT require leader approval and affected-module input.
- Any schema mismatch is a separate schema/migration PR. Do not apply a database change from a documentation PR; do not edit initial migration. Data safety and test DB isolation are mandatory.
- PR plan after leader approves the relevant contract: (1) review/sync Ch4↔main schema and separately plan auth migration; (2) TV1 auth/RBAC foundation; (3) TV2 auth UI/profile/users; (4) TV3 categories Skill/Admin, guidance and recommendations; (5) TV1 Admin opportunity review; (6) TV4 events/reminders/notifications and dashboard; (7) TV5 forum/moderation with TV4 notification + shared logs; (8) integrated end-to-end review. This sequence is not itself an approval or implementation claim.

## 6. Handoff checklist

Before a module implementation starts: (1) owner reads its contract and Ch3/Ch4 source references; (2) verify dependent endpoint/code and current DB migration status; (3) confirm the leader-approved contract and resolve its blockers with the leader; (4) use branch from latest origin/main and isolate test DB; (5) test public, role and ownership boundaries; (6) update implementation state with commit/test evidence; (7) provide cross-module review input on auth, categories, deadlines, logs and notifications. The leader is the only contract approver; no member should re-author a competing contract or claim approval on another's behalf.
